# Backend worker

Node/TypeScript worker that polls the `pipeline_jobs` table (see `../supabase/`) and runs each content request through the pipeline stages. No n8n, no Redis — one process, a Postgres queue, and Claude for every AI step.

## What's here

**Build step 2 — worker skeleton:**

- `src/config/env.ts` — zod-validated environment config; fails loudly at startup if anything required is missing.
- `src/clients/` — thin wrappers around every external service: `supabase.ts` (service role client), `anthropic.ts` (Claude, with a "fast"/"strong" model tier split and a `completeStructured` helper that forces tool-use for reliable JSON), `voyage.ts` (embeddings), `tavily.ts` (search + extract), `firecrawl.ts` (fallback scrape), `youtube.ts` (transcript fetch), `resend.ts` (email), `buffer.ts` (scheduling — OAuth/profile-id wiring lands with the UI in a later step).
- `src/worker/registry.ts` — a stage-name → handler map. Every stage in `src/pipeline/stages.ts` is pre-registered with a placeholder that throws "not implemented", so the worker loop is runnable end-to-end even before every stage exists.
- `src/worker/loop.ts` — `runOneTick` (claim → run handler → advance/requeue/fail, fully unit-tested with fake deps in `loop.test.ts`) and `runWorker` (N concurrent polling slots, bounded by `WORKER_CONCURRENCY`).
- `src/worker/supabaseDeps.ts` — wires `loop.ts`'s abstract deps to real Supabase calls (including the `claim_next_pipeline_job`/`advance_pipeline_job` RPCs).

**Build step 3 — intake stage** (`src/pipeline/intake.ts` + `intakeDeps.ts`):

- `runIntake` (pure logic, unit-tested with fake deps in `intake.test.ts`) extracts every supporting material, asks Claude (via `completeStructured`, "fast" tier) to structure a brief `{topic, audience, tone, overview}`, and decides whether the request can proceed. The model is explicitly told to *omit* `audience`/`tone` rather than guess when it can't confidently determine them from what was actually submitted — `missing_fields` is computed in code from what's present, never invented by the model.
- Blocking is enforced in the stage itself, not just suggested in the UI: if any required field is missing or any source is `blocked`/`unreadable`, the stage returns `nextAction: "stop"` and sets `content_requests.status = 'awaiting_creator'` instead of advancing to research.
- Per-source extraction (`intakeDeps.ts`, `extractSupportingMaterial`): a URL first tries Tavily Extract, falls back to Firecrawl scrape, and is marked `blocked` with a suggestion if both fail; a YouTube link fetches its transcript (free, no API key); an upload (image/PDF) downloads from Supabase Storage and reads it via Claude's native multimodal input; pasted text is recorded as-is.
- Resubmission after a fix isn't handled here — see the DB trigger note below.

**Build step 4 — research, retrieve, rerank:**

- `src/pipeline/research.ts` + `researchDeps.ts`: generates 10-15 search queries from the brief (`completeStructured`, "fast" tier), runs each through Tavily with retry/backoff, and falls back to Claude's server-side web search tool only if Tavily fails outright for that query. A query that exhausts both is logged and the request is marked `degraded` in its activity log rather than failing the stage — partial research beats a hard stop. Every research hit lands in `source_materials` (`origin: "research_result"`), deduped by URL (highest-scoring version wins).
- `src/pipeline/retrieve.ts` + `retrieveDeps.ts`: embeds every `source_materials` row for the request that doesn't have a vector yet (both the research stage's finds and intake's user-supplied sources), batched through Voyage 50 at a time. One vector per source, not per chunk — see the design note in `../README.md` for why that's enough at this scale.
- `src/pipeline/rerank.ts` + `rerankDeps.ts`: embeds the brief itself as a query, pulls the ~10 nearest sources via the `match_source_materials` RPC (cosine distance, verified against a real concurrent Postgres run), then has the model pick and order the top ~5 that actually matter (`completeStructured` again) — this is what keeps the generation stage's context small and avoids lost-in-the-middle. Candidates are referenced by list position in the prompt/schema (not by UUID) so the model can't typo an id it's supposed to select.
- All three are pure-logic-plus-injected-deps like `intake.ts`, unit-tested with fake deps in their respective `.test.ts` files.

**Build step 5 — plan, generate, evaluate (the revise loop):**

This is the first place a stage's next step is decided by data, not a fixed chain, so `StageResult` gained an optional `nextStage` (in `worker/registry.ts`) that overrides the static `NEXT_STAGE` lookup for that one advance — `loop.ts` prefers it when present. `evaluate_article` and (added in step 6) `evaluate_channel` are the two stages that set it.

- `src/pipeline/plan.ts` + `planDeps.ts`: turns the brief + top-ranked sources into a structured outline (title/hook/H2-H3 sections/CTA/keywords), applying the SEO structural rules directly in the system prompt (single H1 via the title, keyword in the first ~100 words, 2-3 sentence paragraphs reflected in how granular the sections are).
- `src/pipeline/generate.ts` + `generateDeps.ts`: fills the outline into `NUM_DRAFT_OPTIONS` (2) full drafts, citing sources by list position (resolved to real `source_material_id`s before storage, same anti-typo pattern as rerank). On any attempt after the first, it pulls the previous evaluation's notes/weak-claims/sections-needing-revision (whichever draft option scored highest, via `rubric.ts`'s `totalScore`) and folds them into the prompt as mandatory fixes — this is what makes "revise" actually change something instead of regenerating blind.
- `src/pipeline/evaluateArticle.ts` + `evaluateArticleDeps.ts`: scores every draft option against `content-evaluation-rubric.md`'s criteria (`rubric.ts`, minus Channel Fit — that one needs `channel_adapt` to exist first), picks the best option (pass beats revise beats reject; ties broken by total score), and decides where the pipeline goes next:
  - **pass** → `channel_adapt`
  - **revise/reject, under `MAX_AUTO_REVISE_ITERATIONS` (3)** → back to `generate`, with feedback
  - **revise/reject, at the cap** → forced through to `channel_adapt` anyway, `needsManualAttention: true` logged so the human reviewer sees it wasn't a clean pass — bounds token spend on a request that just won't converge, per the plan's design.
- `src/pipeline/sourceQueries.ts` / `rubric.ts`: small shared helpers (brief + ranked-source fetch; rubric criteria list, evaluation-detail shape, score totaling) used across plan/generate/evaluateArticle instead of duplicated per file.

**Build step 6 — channel adaptation, its own evaluate/revise loop, and "return to creator":**

- `src/pipeline/winningDraft.ts`: recomputes which article draft `evaluate_article` picked as best (same pass-beats-revise-beats-reject, tie-broken-by-score priority, applied to the latest iteration's evaluations) rather than persisting that decision separately — the `evaluations` table is already the source of truth for it. `channel_adapt` uses this to know what to adapt.
- `src/pipeline/channelAdapt.ts` + `channelAdaptDeps.ts`: turns the winning article into LinkedIn/X/email drafts in one batched call, with `channel-formatting-rules.md`'s per-platform rules (PAS structure for LinkedIn, one-idea-plus-hashtag-limit for X, subject-line-plus-word-count for email) embedded directly in the system prompt. All three channels are generated and revised together as one unit, not independently — simpler than per-channel revision tracking, while still giving each channel its own evaluation score.
- `src/pipeline/evaluateChannel.ts` + `evaluateChannelDeps.ts`: scores each channel draft on the lighter `CHANNEL_RUBRIC_CRITERIA` (channel fit, tone, clarity — `rubric.ts`; the full article rubric's source-grounding/factual-consistency criteria don't need re-checking here since they're inherited from the already-approved article). Same revise loop shape as the article: any channel not passing sends the whole batch back to `channel_adapt`, capped at `MAX_AUTO_REVISE_ITERATIONS`. Once every channel passes, or the cap is hit, this stage calls `markAwaitingCreator` — the pipeline's terminal transition, setting `content_requests.status = 'awaiting_creator'` so the creator now sees the full package (article + 3 channel drafts + evaluation history). This is genuinely the last automated stage; `NEXT_STAGE['evaluate_channel']` stays `null` and nothing further gets queued.
- `src/pipeline/channelQueries.ts`: shared "latest version's channel_drafts" lookup, used by both `channel_adapt` (to pull prior-round feedback) and `evaluate_channel` (to know what to score).

The full automated chain (intake → research → retrieve → rerank → plan → generate ⇄ evaluate_article → channel_adapt ⇄ evaluate_channel → awaiting_creator) is now wired end to end in `src/index.ts`.

**Build step 9 — publishing (Buffer integration):**

`publishing_queue` is a separate queue from `pipeline_jobs` -- it only starts existing once a request is `approved`, has no multi-stage chain, and "publish" is one external call rather than an LLM step, so it gets its own small poll loop instead of another pipeline stage.

- `src/worker/publishingLoop.ts`: `runOnePublishTick` (pure logic, unit-tested with fake deps in `publishingLoop.test.ts`) claims one queued item, looks up that channel's latest `channel_drafts` body, and calls Buffer to create the update (immediate if `scheduled_time` is null, scheduled otherwise). Any failure -- a missing `BUFFER_PROFILE_ID_*`, Buffer's API erroring -- marks the item `failed`, logs an `error_logs` row, and emails every active approver, the same failure shape as the main pipeline worker. `runPublishingWorker` runs this as a single polling slot (publishing volume never approaches the pipeline's `WORKER_CONCURRENCY`).
- `src/worker/publishingDeps.ts`: real wiring -- `claim_next_publishing_item()` RPC (new migration `20250101000013`, same `FOR UPDATE SKIP LOCKED` pattern as the pipeline's job claim), `getLatestChannelDrafts` (reused from `pipeline/channelQueries.ts`), and `buffer.ts`'s `createUpdate`.
- `src/worker/notifications.ts`: `logActivity`/`logError`/`notifyApproverOfError` were duplicated between `supabaseDeps.ts` and the new `publishingDeps.ts`, so they're pulled out here and shared by both.
- **Email is never sent through Buffer** -- Buffer only manages social profiles, not email delivery. Per the plan, email is a manual-send channel: the frontend never inserts a `publishing_queue` row for it at all (the review page just shows the draft for copy/paste). If one somehow shows up anyway, the worker treats it as a bug -- fails it loudly with an error log rather than quietly no-oping -- instead of pretending to have handled it.
- The `content_requests.status = 'scheduled'` transition isn't set by this worker -- it's a DB trigger (`mark_request_scheduled`, migration `20250101000013`) that fires the moment the *first* `publishing_queue` row is inserted for an approved request, following the same trusted-internal-write pattern as `apply_approval_decision`. This means the UI can show "scheduled" the instant the creator submits a time, without waiting on a poll cycle -- Buffer is what actually posts later; this app doesn't poll back for a final `published` confirmation (a future Buffer-status-sync job is what would close that loop, not built here).

**Fixed after real-project testing:**

- **Voyage dimension mismatch:** `retrieve` started failing with "expected 1024 dimensions, not 512" the first time it ran against a real Supabase project -- `voyage-3-lite` actually returns 512-dim vectors, not the 1024 the original schema assumed. Fixed in migration `20250101000014` (column + `match_source_materials`'s parameter type). `scripts/test-voyage.ts` (`npm run test:voyage`) is a standalone script that calls the real `embed()` used by `retrieve.ts` and prints the actual vector size -- useful for catching a provider/model/dimension mismatch in isolation, without needing to run the whole worker.
- **A permanently-failed job never marked the request as errored:** `content_requests.status` has an `'errored'` value, but nothing ever set it -- a job that exhausted its retries got marked `failed` while the *request* stayed on whatever `STAGE_STATUS` left it at (e.g. `'researching'`), looking like it was still in progress. This is also why the frontend's "Errored" dashboard bucket and open-error count silently under-reported. Fixed generically in `loop.ts`'s failure branch: `setRequestStatus(job.request_id, "errored")` right alongside `markJobFailed`.
- **No way to recover a stuck request except resubmitting from scratch:** added `retry_pipeline_job()` (migration `20250101000015`) -- the owning creator or any approver can retry just the failed stage. It's a security-definer RPC rather than a table grant, since `pipeline_jobs` has no direct update policy for `authenticated` and "owner creator OR any approver" isn't expressible as a simple RLS policy without also opening up unrelated writes. `attempt_count` resets to 0 on retry so it gets a full fresh budget instead of immediately re-failing at the cap.
- **Weighted article scoring, replacing the model's own subjective pass/revise call:** `evaluate_article` now only asks the model for 8 raw per-criterion scores (1-5, `EVALUATE_SYSTEM_PROMPT` in `evaluateArticleDeps.ts`); `overall_status` is no longer part of what the model returns. The backend computes it: `weightedScore()` (`rubric.ts`) is `sum(score * weight) / sum(weight)` against `ARTICLE_RUBRIC_WEIGHTS`, compared to `ARTICLE_PASS_THRESHOLD` (3.90):

  | Criterion | Weight | Why |
  |---|---:|---|
  | factual_consistency | 5 | An unreliable article is unusable regardless of how well it reads. |
  | source_grounding | 5 | Research-based content should be traceable to sources, not unsupported claims. |
  | topic_relevance | 4 | Must actually address the intended topic. |
  | audience_fit | 4 | Must match the target audience's knowledge level and interests. |
  | clarity | 4 | Technical ideas need to be understandable. |
  | seo_fit | 4 | Improves discoverability but shouldn't determine whether the content is good. |
  | completeness | 3 | Should sufficiently cover the core idea without major gaps. |
  | tone | 2 | Matters for brand consistency, but a slightly-off tone shouldn't outweigh factual quality. |

  Every place that previously broke ties between draft options by raw score sum (`generateDeps.ts`'s revision-feedback lookup, `winningDraft.ts`, `evaluateArticle.ts`'s `pickBest`) now uses this same weighted score, so "best option" reflects the same priorities as the pass decision. Channel evaluation is unaffected -- it stays on the original unweighted `totalScore()`, since no weighting was requested for that rubric.

- **Targeted regeneration** (`regenerateArticle.ts`/`regenerateArticleDeps.ts`, `regenerateChannel.ts`/`regenerateChannelDeps.ts`): two new stages, `regenerate_article` and `regenerate_channel`, that the creator triggers directly (see `../README.md`) rather than the worker chaining into them. Each is one AI call that updates the existing `article_drafts`/`channel_drafts` row in place -- no new version, no evaluation cycle. `pipeline_jobs` gained a `payload` jsonb column (migration `20250101000019`) to carry the target id and optional instructions, since no existing stage needed per-job parameters before this. Both are terminal (`NEXT_STAGE` maps them to `null`) and deliberately absent from `STAGE_STATUS` (now `Partial`, with `loop.ts` skipping the `setRequestStatus` call when a stage has no entry) -- the request should visibly stay `awaiting_creator`/`changes_requested` throughout, not flip to some in-progress status and back, since conceptually the request is still "awaiting the creator" the whole time.
- **`outline.secondary_keywords.map is not a function`** on the frontend's new Outline tab: the same "forced tool-use is reliable, not guaranteed" issue as `generate`/`channel_adapt`, this time on `plan`'s output -- an already-stored outline had a non-array value where the schema requires one. `planDeps.ts`'s `generateOutline` now validates `secondary_keywords`/`sections` are actually arrays before storing, failing loudly instead of letting bad shape reach the database; the outline tab itself was also made defensive (coerces instead of crashing) since this fix can't retroactively repair data already sitting in a project's database from an earlier run.
- **A request wedged forever at `'evaluating'`:** caught live against a real project -- an `evaluate_article` job got claimed, then its Anthropic API call never returned and never threw. `clients/anthropic.ts`'s client had no request timeout configured (the SDK's own default is 10 minutes), so the worker slot just waited. Fixed with an explicit 120s timeout on the client; the matching database-side fix (reclaiming a job orphaned by a dead worker process, not just a slow call) is `20250101000017_reclaim_stale_jobs.sql`, documented in `../README.md`.
- **`channel_adapt`'s "null value in column \"body\""** reproduced 3 times in a row on the same real request: the schema wrapped LinkedIn/X in a pointless single-field object (`{ body: string }`), which apparently confused the model into emitting stray tool-call-like text for that field instead of a plain string -- `result.linkedin` came back as a string containing literal `<parameter name="body">...` rather than `{ body: "..." }`. Flattened `CHANNEL_DRAFT_SCHEMA` in `channelAdaptDeps.ts` to plain top-level strings (`linkedin`, `x`, `email_subject`, `email_body`) -- no nesting left to misinterpret -- and added a defensive check that throws a clear, specific error naming exactly which field(s) came back empty, instead of letting it surface as an opaque Postgres NOT NULL violation three layers downstream. Confirmed fixed by watching a real retry succeed.
- **`generate`'s `result.options.map is not a function`:** two full article drafts in one structured tool call needed more output budget than `maxTokens: 8192` allowed; a response truncated mid-JSON still comes back as a valid `tool_use` block with incomplete `input`, so the required `options` array was silently missing by the time the code read it. Fixed two ways: `completeStructured` (`clients/anthropic.ts`) now checks `response.stop_reason === "max_tokens"` and throws a clear, specific error naming the tool and budget instead of letting a confusing downstream `TypeError` happen; and `generate.ts` gained `TARGET_WORD_RANGE` (900-1300 words/draft) to bound actual output size instead of leaving it open-ended, which is what really controls token spend (`maxTokens` is just a ceiling, not a cost driver). `TARGET_WORD_RANGE`/`NUM_DRAFT_OPTIONS` are passed into `generateOptions()` as parameters rather than imported into `generateDeps.ts` -- generate.ts already imports `createGenerateDeps` from there, so a reverse import would be circular and hit a real TDZ `ReferenceError` at module load (caught while making this exact change).

**Also fixed in step 6, found while writing the note above:** `content_requests.status` has dedicated values for each stage (`researching`, `retrieving`, `reranking`, `planning`, `generating`, `evaluating`) specifically so the dashboard's queue view can show real progress -- but no stage was actually setting them; status got set once by intake and then sat on `'researching'` through the entire rest of the pipeline. Fixed generically rather than patched per-stage: `worker/loop.ts` now calls a new `setRequestStatus` dep with `STAGE_STATUS[job.stage]` (in `pipeline/stages.ts`) right after claiming a job, before the handler runs. A stage's own handler can still overwrite it afterward (intake's block/advance decision, evaluate_channel's `awaiting_creator`). `channel_adapt`/`evaluate_channel` reuse `generating`/`evaluating` rather than getting distinct values, since the schema doesn't have separate ones for them.

## Setup

```
npm install
cp .env.example .env   # fill in real keys
npm run typecheck
npm test                # unit tests, no network/DB needed
npm run dev              # runs the worker against the .env config
```

`npm test` exercises every stage's pure control-flow logic (`runOneTick`, `runIntake`, `runResearch`, `runRetrieve`, `runRerank`, `runPlan`, `runGenerate`, `runEvaluateArticle`, `runChannelAdapt`, `runEvaluateChannel`, `runRegenerateArticle`, `runRegenerateChannel`, `runOnePublishTick`) plus `rubric.ts`'s `weightedScore()` against fake dependencies — it doesn't hit Supabase or any external API, so it runs without any of the `.env` values set.

## Where a request comes from

There's no HTTP submission endpoint in this backend. The frontend inserts `content_requests` directly via the authenticated Supabase client; a DB trigger (see `../README.md`) auto-enqueues the first `intake` job, and the worker picks it up from there. Resubmission after an intake block works the same way: the frontend updates `status` back to `'intake'`, which re-triggers the same trigger.

**Note:** `status = 'awaiting_creator'` now means two different things depending on how the request got there -- intake couldn't proceed (missing field or blocked source; check `brief.missing_fields`/`brief.blocked_sources`) versus the whole pipeline finished and it's ready for full review (article + channel drafts exist). The frontend (not yet built) will need to tell these apart by checking whether drafts exist, not by status alone; this backend doesn't currently distinguish them with a separate status value.

## Retry/failure behavior

A stage handler that throws gets retried in place (`requeueJob`, same stage) up to `WORKER_MAX_ATTEMPTS` (default 3). Past that, the job is marked `failed`, an `error_logs` row is written, and every active approver gets an email via Resend. This is also where the per-request `token_budget` bookkeeping on `pipeline_jobs` will get consulted once stage handlers exist, so a request that's burning through tokens scales itself down (fewer research queries, fewer draft options) instead of just failing outright.
